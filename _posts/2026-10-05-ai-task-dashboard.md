这个项目最开始就一句话：电脑后台跑 AI 任务，我想用手机遥控它。

不是远程桌面——是真正意义上的"遥控"。人在外面，手机上打开飞书，@一下机器人，发一句"看看现在跑到哪了"，任务进度就回来了；说一句"换个模型再跑"，电脑上那台正在跑的任务就换模型重跑；跑完了，文件直接出现在群里。关掉手机、锁上屏幕，电脑上的任务照跑不误。

断断续续做下来，最后交付的是一个 12314 行的单文件项目。回归测试 605 条用例全绿，真机服务在跑。这篇文章记一下它长什么样、为什么长成现在这样，以及踩过哪些坑。

## 想解决什么问题

痛点其实很朴素：AI 任务（跑 Copilot CLI、训脚本、跑大批量）都挂在电脑上，一旦人离开电脑，就只剩"等"和"猜"。传统方案是远程桌面或者 SSH 隧道，但都有毛病：

- 手机上看远程桌面体验很差，还得保持连接；
- 公网 IP / 内网穿透 / 隧道，配一次错五次；
- 锁屏挂机、关窗口，任务就断。

所以目标定为：**电脑端一个独立常驻进程，飞书自建应用做遥控通道，手机浏览器做看板，全程不需要公网 IP**。

## 为什么是一个 12314 行的单文件

交付物清单：

| 文件 | 说明 |
|---|---|
| `main.py` | 唯一主线交付物（12314 行）：HTTP 服务 + 手机端看板 + 飞书长连接 + 本机执行器 + MCP 服务，全部在一个文件里，只需要 Python 标准库 |
| `README.md` | 完整使用手册（1851 行），日常查用法看它 |
| `main_fastapi.py` | 可选扩展：HTTP 层换成 FastAPI，自带 `/docs`，业务逻辑与 `main.py` 一致 |
| `tasks.db` | SQLite 库：任务、对话、飞书事件留痕、设置，重启不丢 |
| `use-deepseek.ps1` | 一键把 Copilot CLI 的模型来源切成 DeepSeek / Ollama（BYOK） |

单文件 + 标准库是刻意选的：这项目的定位是"丢给别人就能跑"。一个 `main.py`，无 pip、无数据库部署、无前端打包。HTTP 层用 `http.server` 而不是 FastAPI，也是同一个理由——少一个依赖就少一个装不上的理由。需要 `/docs` 交互式文档的时候，用 `main_fastapi.py` 顶上，库结构和业务逻辑完全一致。

## 架构：一体化，没有额外组件

```
手机飞书群 ──@机器人──▶ 飞书长连接（本机出站，不需公网）
                            │
                            ▼
                  main.py（单进程）
        ┌───────────────┼────────────────┐
        │               │                │
   SQLite(tasks.db)   指令路由        本机执行器
   任务/对话/留痕     board_command   copilot -r {session} -p {prompt}
        │               │                │
        └──▶ 内嵌 HTML 看板 ◀────────────┘
                  ▲
        手机浏览器 / 电脑浏览器
```

数据库有九张表：`tasks`（任务）、`messages`（对话）、`task_rounds`（执行流水）、`task_handoffs`（交接摘要）、`feishu_inbox`（事件留痕）、`seen_events`（去重）、`settings`（配置）、`work_reports`（工作汇报）、`hidden_sessions`（黑名单）。所有配置都在库里，重启服务不丢。

## 手机遥控：按钮 = 一条指令

飞书侧的核心设计只有一个：**打字和点击走同一条路由**。卡片上的每个按钮，本质上就是一条预先写好的指令。这个决定保证了永远不会出现"加了功能但遥控器点不到"的情况——按钮就是指令，指令就是按钮。

几个值得说的点：

- 主菜单 + 六个二级页（任务 / 执行 / 模型 / 工作区 / 文件 / 设置），每一页都能点回主菜单，不会走丢；
- 只读卡片**就地刷新**：任务状态一变，群里那张卡片被原地改写，不会堆出一串新卡片；改不动时自动补一张带选项的推送卡兜底；
- 危险动作两步走：`#11 删除` → 回"确认删除 #11"才动手；
- 每一次打字 / 点击都进 `feishu_inbox`，`--feishu-status` 一眼看出按钮通没通。

模型管理也做进了遥控器：三种来源（GitHub 自带目录、环境变量端点如 DeepSeek、自己加的 BYOK 端点），候选清单真去问端点 / CLI（`模型列表`、`测试模型`），不靠硬编码。全局默认 + 单任务覆盖。

## 超时问一句，而不是判失败

跑长任务（训模型、跑大批量）最怕被一刀切超时。这个项目里，到 600 秒不判失败，而是问一句"接着跑 / 停止"；回"继续跑"之后**不限时**，保活盯着进程，只有异常退出才标 `failed`。随时可以 `#11 停止` 掐掉，不必等超时。

长任务本来就不该被掐死，这是这个项目最早的出发点之一。

## 踩过的坑（都已修掉，留档）

- **命令输出里的中文变 `�`**：先按 UTF-8 解，解不开再按本机 ANSI 解；
- **拿 VS Code 的聊天模型名当默认模型**：每条指令都跑失败，后来模型名必须过端点 / CLI 的清单校验；
- **删掉的 Copilot 会话被导入器每隔 30s 捡回来**：加了 `hidden_sessions` 黑名单；
- **轮内提问后 CLI 正常退出，状态被盖成"完成"**：改成留在"待确认"等你回答；
- **只杀 `cmd.exe` 留下孤儿 CLI**：终止时连子进程一起杀；
- **老库升级**：`workdir` / `model` 这类新列自动补上，不用手工 `ALTER TABLE`。

## 验证情况

| 验证 | 结果 |
|---|---|
| 回归用例（离线、假 CLI、假飞书） | 605 PASS / 0 FAIL，覆盖 33 个专题：指令路由、执行重试、模型校验、BYOK、卡片按钮、超时保活、工作区、日志翻页、发文件、推送收敛、就地刷新、撤回 |
| 真机服务 | `/health` 200；飞书长连接"运行中"；卡片按钮通（最近 500 条里收到过 122 次点击） |
| 撤回端到端（真飞书 API） | 真发一条自检消息 → `撤回` 走 `DELETE /im/v1/messages/{id}` 返回 code 0 → 记录清空 |
| 库现状 | 12 条任务（11 完成 / 1 运行中）、275 条飞书事件留痕、17 项设置 |

## 已知限制（用之前请知道）

1. 撤回只在 14 天内——飞书只允许撤同一个应用发的、不超过 14 天、还没被撤过的消息；超期只能"改写成空卡"；
2. 应用缺 `im:message` / `im:message:readonly` 权限，读不到群历史，做不了"翻群聊天记录"；
3. 一个人一个机器人：多个人共用一个应用时，靠各自的 `main.py` 收各自的事件，同一群里两人同时开就会打架；
4. 执行依赖本机 `copilot` 在 PATH 里，登录 / 模型来源得先配好；
5. 手机远程看看板需要网络通路（同 Wi-Fi / Tailscale / 隧道），这是可选项，不配就当电脑端管理中心用；
6. 单机单库，多机协作走交接摘要。

## 还没做（你没要求，算可选下一步）

- 群历史检索（补 `im:message:readonly` 权限后可以做）；
- 精确撤回（`撤回 #N` 按任务号撤某条推送，现在是"最后一张"语义）；
- 真往群里发一次 `README.md`（需要应用补 `im:resource` 权限）；
- 提示词模板 / 片段库（手机上一句话触发整套固定提示词）；
- 多机看板汇总（几台电脑的 `tasks.db` 合并成一个总看板）。

## 一点感想

这个项目和我实习做的编译器方向完全是两种味道：编译器是把一个复杂的东西拆得越来越深，这个项目是把一堆零散的东西（HTTP、长连接、SQLite、命令行执行器、卡片消息）捏成一个能用的整体，而且是"丢给别人就能跑"的那种整体。

最得意的大概是那条规则：**按钮 = 一条指令**。它让打字和点击永远走同一条路，也让这个遥控器永远没有"功能加上了但点不到"的裂缝。

605 条回归用例全绿、真机服务在跑的那天，算是给这个项目画上了一个里程碑。
